2. 需求背景（必填）
*此章节用于描述需求发起的原因、业务背景、需求发起部门，当前已有功能使用现状*ni
- 改造功能背景。
  - 描述当前功能：简述现有功能的处理逻辑、主要流程、关键界面、交互逻辑。
  - 阐述问题/痛点：具体描述当前功能存在的问题、缺陷、低效场景、用户体验问题
  - 提供数据支撑：用户使用情况（使用频率、操作周期、用户活跃数据），问题数据（问题导致的错误率、操作周期延长情况、业务损失估算）、性能瓶颈数据（响应时间、并发处理能力限制）
  - 优化目标：明确本次改造期望能达到的核心效果（解决X问题、实现X功能，提升效率X%、降低错误率Y%、缩短处理时间Z秒等）
- 新增功能（系统）。
  - 描述业务场景： 清晰阐述该功能旨在满足的具体业务场景、用户需求或工作流程。说明当前的工作模式、业务处理流程、存在的痛点。
  - 目标用户/使用部门： 明确指出该功能的主要使用者（角色、部门）以及可能涉及的协作部门。
  - 预估使用情况 (必填项)：
    - 预估上线后的用户规模、使用频率、关键操作量。
    - 预估带来的影响（如：预计处理量提升、预计节省时间/成本等）。
  - 核心价值： 说明新功能上线后能为业务、用户或公司带来的核心价值（如：开拓新市场、提升客户满意度、增加收入、降低成本、提高效率、满足合规要求等）
  - 系统归属： 明确该功能所属的系统名称及其标准英文简称。如果是跨系统功能，说明主系统。
- bug修复。
  - 问题现象： 清晰、具体地描述 Bug 的表现（用户看到的错误信息、数据异常、系统崩溃等）。
  - 影响范围：
    - 受影响的用户范围、功能模块、业务流程。
    - 问题数据：提供可复现 Bug 的具体数据样例、操作步骤、发生时间、频率。
  - 定位原因： 简述技术或业务层面已分析出的根本原因及触发条件（如：代码逻辑缺陷、数据异常、特定输入组合、环境配置问题等）。如果尚未完全定位，说明已知线索和排查方向。
- 外部系统对接（接口交互）。
  - 对接方系统： 明确对方系统名称及其标准英文简称/标识符
  - 当前交互方式： 简述目前双方系统是如何交互的（人工操作、文件传输、 API 等），并指出当前方式的主要问题和局限性。
  - 对接目标： 说明本次对接期望实现的交互流程、数据同步内容、交互频率、实时性要求等。
  - 对接价值： 阐述对接成功后对流程的优化程度。
- 文本配置功能。简述文本适用的场景（部门、业务市场、经销商等），本次改造原因。
- 数据治理需求。简述治理的原因及方案。
