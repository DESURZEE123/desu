## 一、方案概述与核心目标

### 1.1 背景与动因

当前尽调评审系统数据来源**高度依赖核心系统**，每次页面加载、查询、保存都需要跨系统调用核心接口，导致：

- 系统调用效率低下，页面响应慢
- 核心系统耦合度高，可拓展性差
- 核心系统压力大，存在单点故障风险

### 1.2 核心目标

将尽调评审系统中**公共基础服务的核心数据**从"实时调用核心接口"改为"存储本地数据库"，实现：

- 提升系统运行效率（查询走本地库）
- 降低对核心系统的依赖
- 提升后续业务拓展的灵活性

### 1.3 本期范围


| 功能模块 | 改造内容                    |
| ---- | ----------------------- |
| 项目审批 | 项目审批页面中调用核心接口部分内容改为落本地库 |
| 突破定价 | 突破定价页面中调用核心接口部分内容改为落本地库 |
| 品牌管理 | 删除接口查询本地库数据             |


> 文档明确说明：保存、详情页面及逻辑拆分因复杂度较高，后续由各业务系统负责人拆分需**求单独撰写**。

## 二、技术架构分析



### 2.1 架构转变

```
改造前：尽调系统 ←→ 核心系统（实时接口调用）
改造后：尽调系统 ←→ 本地数据库（查询/保存）
         ↓（审核通过后）
       核心系统（异步/批量同步）
```



### 2.2 数据流向设计

- **查询类操作**：全部走本地库，不再调用核心接口
- **保存/提交操作**：先落本地库，项目审核通过后**全量同步给核心系统**
- **审批流状态变更**：尽调系统直接修改本地库单据状态，无需调用核心接口（环卫项目除外）



### 2.3 架构亮点

1. **读写分离思路**：查询走本地，写入审核通过后同步核心，降低核心系统读压力
2. **权限一致性**：通过统一用户管理保持与核心原查询权限一致
3. **多系统归属标识**：通过 `PROJECT_ATTRIBUTION` 字段区分不同尽调子系统（小企业PRJC-SLB、厂商租赁PRJC-DRS、闪光租PRJC-FLR）

## 六、风险与挑战



### 6.1 高风险项


| 风险项          | 风险等级 | 说明                                                |
| ------------ | ---- | ------------------------------------------------- |
| **数据一致性**    | 🔴 高 | 本地库与核心系统的数据同步机制未详细设计，审核通过后全量同步的失败回滚方案缺失           |
| **数据迁移**     | 🔴 高 | 历史数据从核心迁移到本地的方案、时间窗口、校验机制未提及                      |
| **项目复制逻辑**   | 🟡 中 | 涉及4层复制逻辑（核心+公共基础+行业个性化+尽调数据服务），复杂度高，且部分依赖核心接口尚未提供 |
| **表结构未确认**   | 🟡 中 | 需求阶段表结构标注"以研发为准"，可能导致前后端联调返工                      |
| **自动决策接口**   | 🟡 中 | 文档中标注"核心提供接口？"，存在依赖未确认                            |
| **环卫项目特殊处理** | 🟡 中 | 环卫项目仍需调用核心修改状态，与其他项目逻辑不一致，增加维护成本                  |




### 6.2 性能风险

- 列表页查询涉及多表关联（项目基础信息+实施方案+突破定价），需关注SQL性能
- 多报价项目的收益率字段需以";"拼接，大数据量下可能影响查询效率
- 附件本地化存储（EPRK_PUB_BLOB）需考虑存储容量和访问性能



### 6.3 业务风险

- 保存操作整合12个接口，**事务边界不清晰**，部分成功部分失败的处理方案未明确
- 项目复制时若核心接口成功但尽调数据复制失败，仅提示并跳转编辑页，**可能导致数据不完整**
- 客户权限查询、名单查询仍依赖核心，若核心不可用则无法新建项目

## 七、优化建议



### 7.1 架构层面

1. **引入数据同步中间件**：建议使用消息队列（如Kafka/RocketMQ）实现审核通过后的数据异步同步，而非直接接口调用，提高可靠性和可追溯性
2. **增加本地缓存层**：对于客户信息、码值数据等高频查询但低变更的数据，增加Redis缓存，进一步提升性能
3. **设计数据对账机制**：定期（如每日）比对本地库与核心系统数据，及时发现并修复不一致



### 7.2 数据层面

1. **明确数据迁移方案**：补充历史数据迁移的范围、时间、校验规则、回滚方案
2. **完善表结构设计**：需求阶段应确认核心表结构，补充索引设计、字段类型、长度、默认值、注释
3. **增加数据版本字段**：建议在核心表中增加 `CORE_VERSION`（文档中已部分体现）和最后同步时间，便于增量同步和问题排查



### 7.3 接口层面

1. **拆分保存接口**：当前保存操作整合12个接口，建议按业务模块拆分为多个子保存接口，支持分步保存和断点续存
2. **明确事务边界**：定义哪些操作必须在同一事务中，哪些可以异步处理，失败补偿机制是什么
3. **增加接口幂等性设计**：数据同步接口应支持幂等调用，防止重复同步导致数据错误



### 7.4 流程层面

1. **统一审批流逻辑**：建议将环卫项目也纳入本地化逻辑，减少特殊分支，若必须保留则需明确原因和长期规划
2. **确认自动决策依赖**：尽快与核心系统团队确认自动决策接口的提供时间和方案
3. **补充灰度上线方案**：建议按项目类型/部门/用户分批灰度上线，降低全量切换风险



### 7.5 文档层面

1. **补充非功能需求**：当前文档缺少性能指标（页面响应时间、并发量）、可用性要求、数据保留周期等
2. **补充测试策略**：建议明确单元测试、集成测试、数据一致性校验测试的范围和标准
3. **补充上线回滚方案**：若上线后出现严重问题，如何快速回退到原核心接口调用模式

## 八、总结

这份需求文档在**业务功能覆盖**方面较为全面，详细列出了涉及的表、接口、页面字段和操作逻辑，体现了对现有系统的深入理解。方案的核心思路——"查询本地化、写入审核后同步核心"——是合理的，能够有效提升系统性能并降低核心系统压力。

但文档在**技术方案深度**上存在不足：数据同步机制、数据迁移方案、事务边界、异常处理、性能设计等关键技术点尚未明确。建议在进入开发前，组织技术评审会议，重点确认上述高风险项，补充完善技术方案后再行开发。

整体而言，这是一份**业务需求清晰、技术方案待完善**的需求文档，方向正确但需要进一步深化技术设计。
